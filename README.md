# PARTO — سامانهٔ پایش و تحلیل رفتار دانش‌آموزان

نرم‌افزار دسکتاپ (PySide6) برای ثبت مشاهده‌های رفتاری، مداخلات، پیگیری‌ها،
مشاوره، فعالیت‌های فوق‌برنامه و تحلیل‌های آموزشی — با تقویم شمسی و
دیتابیس SQLite.

---

## قابلیت‌های اصلی

| بخش | توضیح |
|-----|-------|
| دانش‌آموزان | پروندهٔ دانش‌آموز، پروندهٔ سالانه، کلاس‌بندی، ارتقای پایه |
| مشاهده‌ها | ثبت رفتار بر پایهٔ شایستگی/شاخص/رفتار قابل مشاهده (ساختار سه‌لایه) |
| مداخلات و پیگیری‌ها | ثبت مداخله، پیگیری نتیجه، یادآوری‌ها |
| مشاوره | جلسات مشاوره، ارجاع، جلسهٔ بعدی |
| فعالیت‌ها و اهداف | فعالیت‌های فوق‌برنامه، اهداف فردی و پیشرفت آن‌ها |
| گزارش‌ها و تحلیل | داشبورد، تحلیل روند، گزارش معلم/کلاس/دانش‌آموز، خروجی Excel و PDF |
| مدیریت | کاربران و نقش‌ها، کنترل دسترسی (RBAC)، لاگ عملیات، پشتیبان‌گیری |

## پیش‌نیازها

- Python 3.9 یا بالاتر
- بسته‌های `requirements.txt`

```bash
python -m venv venv
# ویندوز:
venv\Scripts\activate
# لینوکس/مک:
source venv/bin/activate

pip install -r requirements.txt
```

> بستهٔ `python-magic` **اختیاری** است: اگر نصب باشد، اعتبارسنجی محتوای
> فایل‌های پیوست دقیق‌تر می‌شود؛ در صورت نبودن، تشخیص از روی امضای بایتی
> فایل انجام می‌شود و برنامه بدون آن هم کار می‌کند.

## اجرا

```bash
python main.py
```

در اولین اجرا، دیتابیس در `database/partow.db` ساخته و به آخرین نسخه
مهاجرت داده می‌شود. کاربر مدیر پیش‌فرض در پایگاه‌دادهٔ تازه‌ساخته‌شده
`admin` است و در نخستین ورود، تغییر رمز اجباری است.

```
PARTO/
├── main.py                  # نقطهٔ ورود
├── config/                  # تنظیمات، ثابت‌ها، enums پایه
├── database/                # اتصال، schema، migration ها
├── dal/                     # لایهٔ دسترسی به داده (تمام SQL اینجاست)
├── models/                  # مدل‌های دامنه
├── services/                # منطق کسب‌وکار و اعتبارسنجی
├── views/                   # رابط کاربری (صفحه‌ها، دیالوگ‌ها، ویجت‌ها)

├── tests/                   # تست‌های واحد

```

### قواعد معماری (که در بازرسی‌ها تثبیت شده‌اند)

1. **هیچ SQL خامی در لایهٔ نمایش نیست.** صفحه‌ها و دیالوگ‌ها فقط با
   `dal/` و `services/` کار می‌کنند.
2. **یک منبع زمان:** همهٔ مهرهای زمانی از `utils/time_utils.py`
   (UTC-aware) گرفته می‌شوند؛ `datetime.now()` بدون ناحیهٔ زمانی ممنوع است.
3. **یک قالب تاریخ:** تاریخ‌های شمسی هنگام ذخیره به `yyyy/MM/dd`
   یکدست می‌شوند (ورودی‌های خط‌تیره‌دار مثل `1405-6-6` هم پذیرفته و
   نرمال می‌شوند) و اعتبار تقویمی‌شان بررسی می‌شود.
4. **خطاها بی‌صدا رد نمی‌شوند:** به‌جای `print`، از `utils/logger.py`
   استفاده می‌شود؛ هیچ `except` بی‌لاگ و بی‌توضیحی وجود ندارد.
5. **استثناها در لایهٔ داده مشخص‌اند:** `dal/` فقط `sqlite3.Error` و خطاهای
   نگاشت ردیف را می‌گیرد (`KeyError/TypeError/…`) تا خطاهای برنامه‌نویسی
   پنهان نشوند؛ در عوض `services/` و `views/` به‌عنوان «مرز» عمداً هر شکستی
   را به پیام گویا/`QMessageBox` تبدیل می‌کنند.
6. **پاکی lint:** `ruff check .` روی کل درخت **صفر یافته** می‌دهد. استثنای
   `BLE001` در `services/`، `views/`، `database/`، `utils/`، `models/` و
   `main.py` عمدی است و در `ruff.toml` با عنوان «سیاست مرز خطا» مستند شده؛
   `dal/` از این استثنا بیرون است.
7. **حذف منطقی:** همهٔ موجودیت‌ها `is_deleted`/`deleted_at` دارند و
   کوئری‌ها به‌صورت پیش‌فرض رکوردهای حذف‌شده را برنمی‌گردانند.
8. **تحلیل رفتارمحور (دور ۱۱):** قوت/ضعف از **نوع رفتارهای ثبت‌شده**
   ساخته می‌شود، نه از میانگین شدت؛ الگو باید تکرارشونده باشد (حداقل ۲
   مشاهدهٔ هم‌سو با سهم غالب ۶۰٪) و یک مشاهدهٔ منفرد هرگز نتیجه‌گیری
   نمی‌سازد. شدت فقط «اطلاعات تکمیلی» است. روند = تغییر **ترکیب رفتارها**؛
   تعداد مشاهدات تنها «حجم ثبت و پایش» است و به‌تنهایی بهبود/افت نیست.
   منطق مشترک در `utils/behavior_analysis.py` نگه داشته می‌شود.
   **(دور ۱۳)** جهت روند از **مسیر بین همهٔ بازه‌ها** به دست می‌آید، نه فقط
   از مقایسهٔ اولین و آخرین بازه: بهبود تدریجی با گام‌های کوچکِ هم‌جهت
   «بهبود» است؛ برگشت جهت یا تغییر معنادار میانی که برگشته، «روند
   غیرقطعی» است. هر خروجی روند، «مسیر تغییر بین بازه‌ها» را هم نشان می‌دهد.
   گزارش چندساله (`generate_growth_narrative`) یک **روایت منسجم** است
   (مسیر سال‌به‌سال، الگوهای ادامه‌دار، زمینه‌های تغییریافته با جهت،
   مداخلات مؤثرتر بر اساس پیگیری، جمع‌بندی و اولویت‌ها) و با یک رندر
   مشترک در گزارش معمول، PDF و Excel یکسان دیده می‌شود.
9. **تفکیک لایه‌های اطلاعاتی:** «مشاهدهٔ رفتاری»، «غربالگری» و «تفسیر
   حرفه‌ای» در گزارش‌ها جدا نشان داده می‌شوند؛ نتیجهٔ غربالگری هرگز
   تشخیص یا برچسب قطعی نیست. زمینهٔ خانوادگی و گفت‌وگو با والدین فقط
   «زمینهٔ رشد» است و مبنای قضاوت دربارهٔ خانواده یا دانش‌آموز نمی‌شود.
   مقایسه فقط با خودِ دانش‌آموز در طول زمان انجام می‌شود.
10. **نخ‌ها و دیتابیس (دور ۱۲ و ۱۴):** هر نخ اتصال SQLite خودش را از
    `DatabaseConnection().get_connection()` می‌گیرد؛ اتصال/کاربر جاری/عمق
    تراکنش **نخ‌محلی** است و هرگز بین نخ‌ها دست‌به‌دست نمی‌شود. تراکنش
    سرویس با `BEGIN IMMEDIATE` شروع می‌شود (نویسنده‌ها منتظر می‌مانند، نه
    خطای «database is locked»). آماده‌سازی اسکیما (Migration/ترمیم/تریگرها)
    یک‌بار برای هر نسل اتصال انجام می‌شود، نه برای هر نخ. **هر نخ کارگر باید
    هویتش را صریح اعلام کند:** `with DatabaseConnection().worker_context(uid)`
    برای کاری که به نمایندگی از کاربر انجام می‌شود (uid در نخ UI با
    `get_current_user()` گرفته می‌شود) و `worker_context(None)` برای عملیات
    خودکار سیستم (زمان‌بند)؛ در Audit، `user_id=NULL` یعنی «سیستم».
11. **بدون N+1 (دور ۱۲ و ۱۴):** در حلقه‌ای که روی رکوردها می‌چرخد
    (لیست دانش‌آموزان، مشاهده‌ها، انتساب‌ها) برای هر ردیف `get_by_id` یا
    `get_active_by_student` صدا زده نمی‌شود؛ شناسه‌ها با متدهای دسته‌ای DAL
    (`get_by_ids`، `get_active_by_students`، `get_titles_by_ids`،
    `get_names_by_ids`) یک‌جا خوانده می‌شوند. این متدها **همان معناشناسی**
    نسخهٔ تک‌رکوردی را دارند (حذف‌شده‌ها بیرون، شناسهٔ ناموجود بیرون) و
    فهرست IN را با `utils/batch_query.py` تکه‌تکه می‌کنند.
12. **حسابرسی کامل (دور ۱۲ و ۱۴):** هر ۱۸ جدول حساس پنج تریگر
    `insert/update/soft_delete/restore/hard_delete` دارند که تصویر کامل
    ردیف (JSON) را قبل/بعد ثبت می‌کنند (بدون `password_hash`). سرویس‌ها
    برای همین اقدام‌ها ردیف دستی نمی‌سازند (`BaseService.log_audit` تکراری
    را رد می‌کند). اتصال‌های خام بیرون از برنامه برای نوشتن/حذف روی این
    جدول‌ها باید تابع `get_current_user_id` را ثبت کنند.
